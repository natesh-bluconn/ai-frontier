# Auth & Security

### SEC-1: Every `@AllowUnauthenticated()` must be justified

**Severity:** blocker
**Check:** New or changed `@AllowUnauthenticated()`. Default answer is no. Public endpoints that exist (webhooks, captcha'd forms, one-time-token flows) must validate something (signature, header key, one-time token) and must not throw `UnauthorizedException` as their "auth".
**Say:** "why AllowUnauthenticated?" (×20+) · "why this has to be allowed Unauthenticated? Logged in user only will be creating the new user right?" (#164) · "this should never throw UnauthorizedException as it is allowed Unauthenticated" (#809) · "add captcha validation" (#783)

### SEC-2: Admin / permission-scoped endpoints

**Severity:** blocker
**Check:** Endpoints that manage configs, credentials, migrations, charts, module access, views, cross-account data, workflow triggers, support admin actions → `@AllowAdminUser()` or a permission check. Watch for a controller-level `@AllowAnyAuthenticatedUser()` silently applying to a new admin endpoint.
**Say:** "only allow admins" (×15+) · "we should only allow admins to access these" (#1901) · "top level AllowAnyAuthenticatedUser will always allow this for other users too" (#3337) · "only users with specific permission should be allowed to exit an account" (#2099)

### SEC-3: Tenant isolation — every query scoped by `accountId`

**Severity:** blocker
**Check:** GET/list/update/delete without `accountId` in the where clause; resources looked up only by id; resuming/reusing artifacts across accounts (`resumeFromRunId`); vendors listing all accounts.
**Say:** "we are not passing `accountId` here. Every get call should only return that accounts data" (#106) · "get templates per account" (#548) · "Nothing checks that the prior run belongs to the same account" (#3558)

### SEC-4: Extend auth with decorators/guards, not hacks

**Severity:** should-fix
**Check:** New guards that duplicate `AuthGuard`; special-casing in `auth.service.ts`; hardcoded token types in the guard. Add a decorator (like `AllowUnauthenticated`) or a dedicated guard; one-time-token decorators should take allowed types as a list. Use `@AuthUserParam` instead of re-reading the request.
**Say:** "you don't need a separate guard for this just a new decorator is enough. Check AllowUnauthenticated implementation" (#590) · "instead of this hack lets create a separate auth guard to allow suspended accounts" (#2099) · "this should not be hard code to \"FORM\" type should come as an input from AllowFormToken" (#3184)

### SEC-5: Secrets & tokens

**Severity:** blocker
**Check:** Logging tokens/passwords; storing passwords in DB; caching decrypted creds; returning auth fields in list responses; tokens/expiry generated by the client; reading `process.env` directly instead of config; test-only endpoints reachable outside `NODE_ENV=test` without a header key.
**Say:** "don't print tokens" (#1104) · "this password shouldn't be stored in the DB" (#36) · "if we need list make sure you remove auth stuff in response" (#3009) · "token should be created by backend. even expiresAt is decided by backend" (#941) · "don't use env vars directly instead load via config" (#809)

### SEC-6: Use the right verifier

**Severity:** should-fix
**Check:** Manual `jwt.decode`, extra JWT packages. Use `aws-jwt-verify` (`JwtVerifier` for other IdPs); `verify` already decodes.
**Say:** "no need of separate of this new package. We can validate using JwtVerifier from aws-jwt-verify" (#884) · "you don't have decode manually verify function will do that check too" (#884)

### SEC-7: Identity semantics

**Severity:** should-fix
**Check:** Email passed as `userId`; phone number used where `managerId`/`employeeId` exists; user modeled as multi-org when it's single-org/multi-account; device trust tokens not bound to user.
**Say:** "why email is being passed on userId?" (#2099) · "user should belong to single org but can have access to multiple accounts" (#2133) · "If it just has device info two users logging in from same device will have issues" (#2564)
